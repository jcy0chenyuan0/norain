# 0011 阻断（隔离）模块的默认状态与恢复

- 状态：已接受（2026-11-14，按最初目标修订，见文末）
- 日期：2026-11-14
- 关联：原稿「阻断模块」「启动模块」；ADR 0005、0007、0013

## 背景

隔离会修改防火墙，阻止除代理以外的出站连接。操作失误会让用户完全断网，所以它的风险高于其他模块。原稿要求它作为独立阶段，并给出了安全默认值：启动时保持隔离，等用户执行恢复命令。

## 建议

1. **默认关闭**。首个版本不实现。实现后的第一版只提供手动 `norain firewall isolate`，不自动触发。自动触发另立 ADR。
2. **自有规则空间**：
   - Linux：只在 nftables 中的独立表 `inet norain` 里操作，删除这张表即可完全恢复，不碰用户的其他规则。
   - Windows：使用固定名称前缀 `Norain-Isolation-` 的 Windows 防火墙规则，并在进入隔离前快照默认出站策略。
3. **允许的连接**（`isolation_allowlist` 之外的固定项）：回环地址；DHCP；代理服务器的 IP 和端口（按协议区分 TCP/UDP）；用户明确列出的局域网网段。
4. **事务**：先快照，再应用；应用失败则自动回滚。进入隔离前把原因、影响范围、规则版本和恢复命令写入 `<state_dir>/isolation.json`，并显示给用户。
5. **恢复**：`norain firewall restore` 完全在本地执行，只读快照，不需要网络和代理，也不依赖其他 Norain 组件正在运行。另外提供一条不依赖 Norain 的手工恢复命令，写在 `isolation.json` 和文档里：
   - Linux：`nft delete table inet norain`
   - Windows：用 PowerShell 按规则名前缀删除规则
6. **启动时**：发现处于隔离状态时保持隔离，并提示恢复命令；只有带 `--restore-isolation` 参数才自动恢复。
7. **测试**：模拟后端覆盖应用、回滚和恢复；真实环境只在一次性虚拟机中测试。

## 修订

2026-11-14，用户：**以最初目标（docs/reference/original-goals.md）为准，除非有硬性 bug。**

「与最初目标的差异」表中，全部采用最初目标一栏：

- 自维持模块修复失败后**自动**进入阻断，同时杀死其他模块并弹窗提醒。
- 启动模块运行时**自动恢复**为非阻断模式。
- 阻断模式下可以用命令行手动解除。

2026-11-18，用户：**改为「立刻阻断，再修复」**（上一条「修复失败后自动进入阻断」被本修订取代）。

- 故障一确认就**立即阻断**，修复在阻断状态下进行；不再有「先修几轮、修不好再断」的暴露窗口。
- 修复窗口放行**固定回环网段 + 代理服务器 + 蓝名单**。国内 DNS 和监控探测目标不放行。
  蓝名单必须放行：它的本意就是「别处都断了这些也要能用」，而修复可能持续几十秒甚至到人工
  介入为止，这时连它一起断掉违背了蓝名单存在的意义。
- 蓝名单在修复期间可达，会让 `monitor.verify` 有可能被误判成「已恢复」，所以 verify 自己
  跳过落在放行范围里的探测项（`monitor._drop_exempt`）：剔除后再判，且要求国内/国外两类
  都还剩足够样本；样本不足一律判失败，绝不把「没证据」当成「已恢复」。
- 修复成功 → 把放行范围收回到完整范围（`block.tighten`）→ 自动解除阻断。
- 修复失败 → 保持阻断退出，与修订前最终效果一致。
- 收紧放行范围失败时**中止**解除阻断：此时系统里可能一条阻断规则都不剩，再继续解除
  会把残缺状态当成恢复成功。收紧后仍装不回修复窗口的窄范围时，状态被标为 `broken`
  并停止自称「已阻断」，`norain block off` 需要 `--force` 才执行，避免误导。

保留的安全措施不改变行为，只防止硬性故障：规则放在独立的表或固定前缀下、应用前快照、失败自动回滚、恢复命令不依赖网络。上文「默认关闭、第一版只能手动触发」「启动时保持隔离」两条作废。
